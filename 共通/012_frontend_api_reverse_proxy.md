# フロントエンドからバックエンド API への接続方式

- 決定日: 2026-09-08
- 状態: 承認

## 背景

フロントエンド（Vue の SPA）とバックエンド（FastAPI）は別のプロセスとして動く。
開発時は Vite の dev サーバーが画面を配信し、API は別ポートの FastAPI が受ける。
このままではブラウザから見て**別オリジン**になり、素の `fetch` は同一オリジンポリシーで
弾かれる。バックエンドには CORS ミドルウェアが入っていないため、何らかの対処をしないと
画面から API を 1 本も呼べない。

決めなければならないのは「**開発時にブラウザからバックエンドへ届かせる経路をどう作るか**」。
これは開発環境だけの話に見えて、実際には次の 3 つに波及する。

- **本番の配信構成** … 開発と同じ経路にするのか、別物にするのか
- **認証方式** … Cookie を使うなら、オリジンが同じかどうかで挙動が変わる
- **バックエンドの改修要否** … CORS を入れるならバックエンドに手が入る

影響を受けるのは `docker-compose.yml`、フロントエンドの Vite 設定、nginx の設定ファイル、
および（案によっては）バックエンドのアプリ生成部分。

## 選択肢

### 案 A

**nginx コンテナをリバースプロキシとして前段に置く。**
ブラウザは nginx の 1 ポートだけを見る。nginx が `/api/*` をバックエンドへ、
それ以外をフロントエンドへ振り分ける。バックエンドのルートは `/health` `/samples` であって
`/api/health` ではないので、**転送時に `/api` プレフィックスを落とす**。

利点 /
- ブラウザから見て**同一オリジン**になるため、CORS そのものが不要になる
- 本番でもフロントのビルド成果物を nginx に置いて配信する想定なので、
  **開発と本番で `/api` の経路が同じ**になる
- Cookie ベースの認証を将来入れたとき、`SameSite` や `credentials` の扱いが
  開発と本番で食い違わない
- バックエンドを一切改修しない

欠点 /
- 開発環境の構成要素が 1 つ増える。画面が出ないときの切り分け先が増える
- Vite の HMR は WebSocket を使うため、nginx 側に `proxy_http_version 1.1` と
  `Upgrade` / `Connection` ヘッダの転送が要る。ここを落とすと
  「保存しても画面が変わらない」という分かりにくい形で失敗する
- 「開発と本番が同じ」と言えるのは `/api` のブロックだけで、`/` の扱いは
  dev（Vite へプロキシ）と prod（静的ファイル配信）で分かれる

### 案 B

**Vite dev サーバーのプロキシ機能を使う。**
`vite.config.ts` の `server.proxy` で `/api` をバックエンドへ転送する。

利点 /
- 追加のコンテナが要らない。設定はフロントエンドの設定ファイル数行で済む
- HMR は Vite が自前で面倒を見るので、WebSocket の設定を書かなくてよい
- バックエンドを一切改修しない

欠点 /
- **この経路は開発時にしか存在しない。** 本番では Vite dev サーバーが動かないため、
  別途リバースプロキシか CORS が必要になり、結局この決定をやり直すことになる
- 開発と本番で経路が違うため、Cookie 認証を入れたときに開発で通ったものが
  本番で通らない、という形の食い違いが起きうる

### 案 C

**バックエンドに CORS ミドルウェアを入れる。**
フロントエンドは `http://localhost:8000` を直接叩く。

利点 /
- 追加のコンテナもプロキシ設定も要らない
- フロントエンドとバックエンドを独立に配置できる（別ドメインでも動く）

欠点 /
- **バックエンドに改修が入る。** 許可オリジンの管理が環境ごとに必要になり、
  設定を間違えると本番で全開放になる事故につながる
- 常に別オリジンなので、Cookie を使う認証では `SameSite=None` + `Secure` が必要になり、
  ローカル開発（http）での取り回しが面倒になる
- プリフライトリクエストの分だけ往復が増える

## 決定

**採るのは案 A（nginx リバースプロキシ）。**

理由:

- **本番の姿から逆算した。** 本番はフロントをビルドして nginx に置く構成にする方針が
  先にあり、そこでは `/api` を nginx が振り分ける形になる。開発だけ別の経路
  （案 B）にすると、同じ問題を本番で解き直すことになる
- **同一オリジンを開発時から確保できる。** これは将来 Cookie ベースの認証を入れる際に効く。
  案 B / 案 C はいずれも「開発では通るが本番で挙動が変わる」余地を残す
- **バックエンドを触らずに済む。** 案 C はバックエンドに許可オリジンの管理という
  運用上の負債を持ち込む
- nginx を足すコストは、コンテナ 1 つと設定ファイル 1 本。
  上の 3 点に対して見合うと判断した

**プレフィックスの落とし方**（実装方針で確定）:
`location /api/`（末尾スラッシュあり）と `proxy_pass http://api:8000/;`（URI 部分あり）を
組み合わせる。nginx はマッチした location のプレフィックスを `proxy_pass` の URI に
置き換えて転送するため、`/api/health` は `http://api:8000/health` になる。
`proxy_pass` から末尾スラッシュを外すと元の URI がそのまま渡り、バックエンドに
`/api` 付きのルートが無いため 404 になる。

## 何を捨てたか

この決定で諦めたこと。**後から「なぜできないのか」と聞かれる箇所**を先に書く。

- **バックエンドは、別オリジンのクライアントから直接叩けない。** CORS を入れていないため、
  別ドメインの SPA・モバイルアプリ・外部システムが直接 API を呼ぶ要件が出たら、
  その時点で CORS の設定を追加する判断が要る（この決定はそれを禁じるものではない）
- **フロントエンドを単体で `npm run dev` して API を叩く、という動かし方はできない。**
  nginx を通さないと `/api` が解決しないため、開発時も compose で起動する前提になる
- **開発環境の起動が nginx に依存する。** 画面が出ないとき、原因が
  Vite / nginx / バックエンドのどれかを切り分ける必要がある
- **「開発と本番が同じ構成」は `/api` の系統に限られる。** `/` の系統は dev と prod で
  nginx の設定が別物になるので、prod の設定を書くときに差分が出る

## 覆すとしたら

- **バックエンドを別オリジンのクライアントから直接叩く要件が出たとき。**
  その時点で CORS が必要になり、「同一オリジンで済ませる」という前提が崩れる
- **本番の配信をリバースプロキシを持たない基盤に載せると決めたとき**
  （静的ホスティング + API ゲートウェイのような構成）。
  「本番と揃える」という決定理由の根拠が消えるため、開発だけ nginx を維持する意味が薄れる
- **HMR や切り分けの手間が実際に開発効率を落としていると分かったとき。**
  開発時だけ案 B に寄せ、本番の nginx とは別物と割り切る判断もありうる
