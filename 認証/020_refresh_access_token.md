# アクセストークンをリフレッシュする

## このユースケースは何をするか

リフレッシュトークンの Cookie を検証し、新しいアクセストークンと**新しいリフレッシュトークン**を
発行する（ローテーション）。使われた旧リフレッシュトークンはその場で失効させる。

要望 00027 で実装済み（`POST /auth/refresh`。`app/application/auth/usecase.py` の
`RefreshAccessTokenUseCase`、`app/interface/auth/controller.py`）。認証対象外のエンドポイント
（アクセストークンではなくリフレッシュトークンで検証するため。`PUBLIC_PATHS` に
`/auth/refresh` を含む）。

## 入力

| 論理名 | 物理名 | 型 | 必須 | 備考 |
| --- | --- | --- | --- | --- |
| リフレッシュトークン | `refresh_token`（Cookie） | 文字列 | ○ | Cookie からのみ受け取る。`Authorization` ヘッダは対象外（リフレッシュはヘッダ両対応の対象に含まれていない） |

## 出力

| 論理名 | 物理名 | 型 | 備考 |
| --- | --- | --- | --- |
| アクセストークン | `access_token` | 文字列 | ログイン API と同じ `AuthSessionResult` を返す。ボディに含める。③で確定 |
| トークン種別 | `token_type` | 文字列 | 常に固定値 `"bearer"`。ログイン API と同じ `AuthSessionResponse` を使う。⑤で追記 |
| ログイン中のユーザー情報 | `user`（`id` / `user_code` / `login_id` / `email`） | オブジェクト | ログイン API と同じ形。ボディに含める。③で確定 |

**副作用**

- リフレッシュトークンに対応する `refresh_tokens` の行を `revoked = true` に UPDATE する（失効）。
- `refresh_tokens` に 1 行 INSERT する（ローテーション後の新しいリフレッシュトークン）。
- **失効と新規発行は同じトランザクションで行う**（片方だけ実行された状態を作らない）。
- 新しいアクセストークン Cookie・新しいリフレッシュトークン Cookie をセットする。

| アグリゲート | 読み書き | 何のために |
| --- | --- | --- |
| [018_refresh_token](018_refresh_token.md) | 書き換える | 旧トークンの失効確認・失効、新トークンの発行 |

## 例外

| 条件 | 結果 |
| --- | --- |
| リフレッシュトークンの Cookie が無い | **401** |
| リフレッシュトークンの署名が不正、または期限切れ | **401** |
| リフレッシュトークンに対応する `refresh_tokens` 行が無い、または既に `revoked = true`（再利用） | **401**。**リプレイ検知（そのユーザーの有効なトークンを全て失効させる）は今回実装しない**（③で確定。[018_refresh_token](018_refresh_token.md) 参照） |

ログイン API と同じ形）、リプレイ検知時の一括失効を今回実装するか（実装しない）。
「認証済みリクエストのたびにアクセストークンを再発行する」件は、ログイン中のユーザー情報取得
を含む全保護対象エンドポイントに掛かる**横断的な仕組み**（`interface/shared/auth.py` の認証依存
`authenticate_request` の中）として実装すると結論した。本ユースケース（リフレッシュ）は
ローテーションそのものとして常に新しいトークンを発行するため、この横断的な仕組みとは別（元々の設計どおり影響なし）。
